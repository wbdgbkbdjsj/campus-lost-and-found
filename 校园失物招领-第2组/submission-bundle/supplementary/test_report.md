## 3 测试策略（三层）

**为什么必须分三层**：三层回答的问题不同，不能互相顶替——**单元层**证明「规则本身对不对」，**集成层**证明「跨层数据落没落对」，**确认层**证明「用户可见的业务流程能不能走完」。冒烟主链属于集成与确认层，**不能拿它冒充单元测试**，否则报告一被追问「你们单元测试怎么做的」就答不上来。

### 3.1 单元测试（Unit Test）

| 项 | 内容 |
| --- | --- |
| 被测单元 | `state_machine.py` 的状态迁移纯函数（输入「当前状态 + 事件 + 上下文」，输出「目标状态」或「错误码」）；`service.py` 中的权限判定与不变量校验；枚举/字典常量 |
| 测试隔离 | 不启 HTTP、不连数据库，直接以函数调用构造 (from_status, event, actor) 三元组断言结果；状态迁移表以数据驱动方式表达，可穷举 8 态 × 事件 |
| 用例来源 | 契约 v1 §5.2 的 12 条合法迁移全表 + 终态封闭（I1）+ I1–I7 |
| 已实跑断言（4 项） | `COMPLETED + APPROVE → 40001`；`COMPLETED + CANCEL → 40001`；`RETURN/REQUEST_INFO` 缺 comment `→ 40003`；不存在单据 `→ 40401`（资源不存在优先于状态判断） |
| 结论 | 规则层 4 项断言实跑通过；**8 态 × 事件组合的完整单元测试集（`测试用例表.md` TC-ST-01~13 等）为设计用例，尚未逐条独立执行，不写作通过** |

```

TC-ST-02  COMPLETED + CANCEL                  -> 40001 「终态不允许事件」      实跑通过
TC-ST-03  UNDER_REVIEW + REQUEST_INFO(空)     -> 40003 「必须填写原因/意见」   实跑通过

```

数据一致性证据（冒烟第 6 节原文，直接贴入报告）：

```
None          --SUBMIT   --> SUBMITTED     | 申请人提交认领申请
SUBMITTED     --ACCEPT   --> UNDER_REVIEW  |
UNDER_REVIEW  --APPROVE  --> APPROVED      | 凭证与物品一致
APPROVED      --VERIFY   --> APPROVED      | 核验不通过：到场人与申请人不一致
APPROVED      --VERIFY   --> APPROVED      | 核验通过：学号/姓名与申请人一致
APPROVED      --HANDOVER --> COMPLETED     | 已核验学号，现场交接
```

> 这段同时证明两件事：**VERIFY 是 `APPROVED` 自环，只写流水不改状态**；**I7（交接前必须有核验通过流水）真实生效**。这两点是答辩最容易被追问的地方。
