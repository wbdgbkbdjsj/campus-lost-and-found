# 设计说明书 — 校园失物招领与认领审核系统（审核端模块 · 李子研）

> 依据：`api-contract-v0.md`（已冻结）。本文档描述系统的总体设计、数据库设计、核心状态机设计与 B 端审核模块的详细设计。

## 1. 系统概述

系统解决校园失物招领中"认领无凭证、审核无流程、交接无记录"的问题。核心是一条**认领单审核状态流**：申请人提交凭证 → 审核员接单审核（可退回补充）→ 通过后线下领取 → 交接确认闭环，全程留痕可追溯。

## 2. 总体架构

```
┌─────────────┐   ┌─────────────┐
│  A端 用户端  │   │  B端 审核端  │
│ 提交/查询/补 │   │ 队列/审核/交接│
└──────┬──────┘   └──────┬──────┘
       │  REST /api/v1   │
┌──────▼─────────────────▼──────┐
│        FastAPI 应用层          │
│  auth │ items │ claims │ review│
├───────────────────────────────┤
│  状态机引擎 state_machine.py   │  ← 唯一合法迁移入口
├───────────────────────────────┤
│  SQLAlchemy ORM + SQLite      │
└───────────────────────────────┘
```

分层：接口层（FastAPI 路由，只做参数校验与鉴权）→ 领域层（状态机引擎，唯一裁决合法迁移）→ 持久层（ORM 模型）。**状态迁移逻辑只存在于 state_machine.py 一处**，路由不得直接改 claim.status。

## 3. 模块划分

| 模块 | 职责 | 归属 |
|---|---|---|
| auth | 注册/登录/token | A 端同学 |
| items | 拾获登记/失物启事 | A 端同学 |
| claims | 认领申请提交/查询/补充 | 共用 |
| **review** | 审核队列、接单、通过、驳回、退补、交接、撤销、超时失效 | **本模块（B 端）** |
| notify | 站内通知 | 共用 |

## 4. 数据库设计

7 张表（user / lost_item / found_item / claim / review_record / notification / audit_log），完整字段见契约 §2。关键设计决策：

1. **claim 与 review_record 分离**：claim.status 只存当前态，review_record 以流水形式记录每次迁移（from→to+action+comment），两者互相印证，支持回放完整审核历史。
2. **found_item.status 与 claim 状态联动**：APPROVE 时 found_item→PICKUP_PENDING（防止重复认领），HANDOVER 时→CLAIMED。
3. **deadline 字段支撑超时**：PENDING_INFO 与 APPROVED 两态可携带截止时间，由 expire-run 批处理统一扫表置 EXPIRED。
4. 外键：claim→found_item、claim→applicant(user)、review_record→claim，全部建立索引。

## 5. 核心设计：认领单审核状态机

8 状态 12 条合法迁移，事件驱动（event: ACCEPT/APPROVE/REJECT/REQUEST_INFO/RESUBMIT/HANDOVER/CANCEL/EXPIRE），迁移规则以二维表 `(from_state, event) → (to_state, actor, side_effects)` 描述，状态机图见 `设计模型/02-状态机图.md`。

设计要点：
- **单一裁决点**：`apply_transition()` 先查迁移表，非法迁移抛 `ILLEGAL_TRANSITION(40001)`，从机制上杜绝"驳回后再通过"之类的脏路径。
- **伴随动作与迁移原子绑定**：通过/交接同步更新物品状态、写审核记录、发通知，在同一事务内完成。
- **终态封闭**：四个终态不再出现在迁移表的 from 列中，天然不可再迁移。
- **超时兜底**：待补充、待领取均设 deadline，超时由系统事件 EXPIRE 收敛到终态，避免单据长期挂起。

## 6. B 端审核模块详细设计

接口（前缀 /api/v1/review，均要求 admin 角色）：

| 接口 | 前置条件 | 后置条件 |
|---|---|---|
| GET /review/queue | 登录 | 返回 SUBMITTED 单按提交时间升序 |
| POST /claims/{id}/accept | 状态=SUBMITTED | 状态=UNDER_REVIEW，锁定 reviewer_id |
| POST /claims/{id}/approve | 状态=UNDER_REVIEW 且 reviewer=当前人 | 状态=APPROVED，物品→PICKUP_PENDING |
| POST /claims/{id}/reject | 状态∈{SUBMITTED,UNDER_REVIEW}，comment 必填 | 状态=REJECTED |
| POST /claims/{id}/request-info | 状态=UNDER_REVIEW | 状态=PENDING_INFO，deadline=+7 天 |
| POST /claims/{id}/handover | 状态=APPROVED 且 reviewer=当前人 | 状态=COMPLETED，物品→CLAIMED |
| POST /review/expire-run | — | 扫描超时单置 EXPIRED |

## 7. 安全与异常设计

- 鉴权：Bearer Token（登录签发，内存会话表）；B 端接口统一 admin 角色校验，返回 40002。
- 越权：申请人只能撤销自己的单据；审核员只能操作自己已接单的单据。
- 异常：非法迁移 40001、参数缺失 40003、资源不存在 40401，统一返回结构 `{code, message, detail}`。
- 并发：接单动作使用状态条件更新（仅 SUBMITTED 可 ACCEPT），重复接单返回 40001 而非覆盖。

## 8. 设计取舍记录

| 决策 | 备选 | 取舍理由 |
|---|---|---|
| 事件驱动状态机（迁移表） | if-else 散落在路由 | 迁移集中可测，契约/代码一致性易核对 |
| 流水表 review_record | 只更新 status 字段 | 可追溯、可回放，答辩审计点 |
| deadline + 批处理扫表 | 每单起定时器 | 实现简单，课程场景足够 |
| SQLite 单文件 | MySQL | 零部署依赖，ORM 隔离便于切换 |
