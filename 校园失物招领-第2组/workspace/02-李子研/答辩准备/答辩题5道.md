# 答辩准备 · 自己模块 5 道问答题（v1）

> 针对"B 端审核状态流"交付物。每题：30 秒口头回答 + 可能追问。v1 更新点：三角色、身份核验 I7、双轨技术栈口径。

---

## Q1 为什么用状态机，而不是在业务代码里写 if-else 判断？

**答**：这个模块的风险不是"功能没做出来"，而是"状态被绕过"。如果每个接口自己 `if status == 'UNDER_REVIEW': claim.status = 'APPROVED'`，只要一个接口漏判，就会出现"驳回后又被通过""超时单还能交接"这类脏数据，而这类错误测试很难覆盖全。

所以我把迁移规则抽成一张表 `(from_state, event) → (to_state, 允许角色, 是否必填意见)`，8 状态 12 条边集中在一处，所有接口只能通过 `apply()` 进入：先查终态、再查边、再查角色、再查必填意见，任何一条不满足直接抛 40001/40002/40003。全仓库只有一处代码真正写 `claim.status`。

好处有三：漏洞只可能出在一个地方；这张表可以和契约、状态机图逐条勾对（《接口-代码检查表》第二节就是 12 条边逐条核对）；迁移到全组约定的 Spring Boot 时，这张表原样变成 state-machine 构件，逻辑零重设计。

**追问：那状态机图不是白画了？** 不是，代码里的表和图上 12 条边是同一份数据，图上没有的边代码里也不存在，两边互为校验。

## Q2 8 个状态是不是太多了？PENDING_INFO 能不能并进 UNDER_REVIEW？

**答**：不能合并，因为它们的**责任人和时限**不同。UNDER_REVIEW 的责任在审核员，可以挂着；PENDING_INFO 的责任在申请人，必须带 deadline、超时自动失效。合并了就无法回答"这单卡在谁手里、卡了多久"，也没法做超时清理。

反过来我也克制过：核验通过后没有设 VERIFIED 状态。因为身份核验不改变"可执行的事件集合"——核验完还是只能交接或超时——按我们的判据（状态只因可执行事件集合不同而拆分），它不配成为一个状态，做成 APPROVED 上的自环、只写一条核验流水就够了。加状态徒增两条边，还稀释了状态图的信噪比。

## Q3 为什么交接前要强制身份核验？这个接口为什么独立出来？

**答**：任务卡要求防冒领，最初版本我只在交接的 comment 里写了"已核验学号"——验收时被指出这是文字约定不是机制约束，核验可能被跳过。v1 改成了两道锁：

第一，**独立接口** `POST /review/claims/{id}/verify`：审核员录入到场人的学号姓名，系统与申请人比对，结果（无论真假）都写一条 VERIFY 流水，from=to=APPROVED，状态不变。
第二，**交接前置**（不变量 I7）：handover 会检查本单是否存在"核验通过"的流水，没有直接 40003，提示"交接前必须先通过身份核验"。

这样冒领场景有两层证据：错误核验的流水记录了到场人是谁，事后可追责；未核验的单在机制上根本走不到 COMPLETED。冒烟测试里这三条（未核验拦截、错信息、通过后交接）都是单独的用例。

**追问：核验失败为什么也放行请求（返回 verified=false 而不是报错）？** 因为"人不匹配"是核验的正常业务结果而不是系统错误，记下来比报错更有价值——它留下了冒领未遂的现场证据。

## Q4 驳回是终态，申请人发现材料交错了怎么办？审核员请假单据锁死怎么办？

**答（前半）**：驳回终态只约束"这张单"，不约束"这个人"，他可以对同一物品重新提交一张。我特意没做"驳回后原地复活"的边：同一单里出现"驳回→通过"，事后无法区分是复核还是审核员反悔，审计链就脏了。驳回时物品自动回退 REGISTERED，废单不占物品。

**答（后半，已知局限）**：当前接单后其他审核员确实动不了这单，审核员请假单据会卡住。继续做会加两条边：TRANSFER 转派（reviewer→reviewer，写流水留痕）和超时回收（接单 N 小时无操作自动回队列）。这两条都不改状态集合、只加边——正好验证了表驱动状态机的扩展成本是可控的。

## Q5 技术栈为什么文档写 Spring Boot、代码却是 FastAPI？（双轨口径）

**答**：这是组长拍板的双轨方案 C。全组约定 Vue3 + Spring Boot + MySQL，四份组级文档都写死了；我的 FastAPI 版定位是**审核状态流的原型加演示保底**：状态机表、9 张表结构、24 项冒烟测试都是现成的，Spring Boot 版按构件映射逐文件翻译即可（映射表在《接口-代码检查表》§五），设计不需要返工。而正式环境没就绪时，D2 彩排和答辩现场随时可以用原型起服务演示，不会开天窗。

对我自己模块而言，状态机、流水、核验这些核心逻辑与框架无关——恰恰因为我们把规则收敛在一张纯逻辑的表里，换框架的代价被压到了最小。

**追问：如果老师只认 Spring Boot 怎么办？** 交两样东西：正式方案按约定技术栈的完整设计文档与部署图，原型作为附录证明流程逻辑已被 24 项自动化测试验证过。文档口径全组一致，不会互相打架。
