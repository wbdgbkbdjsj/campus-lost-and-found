## 3　测试策略（三层，替换原第 3 节）

按指导书要求分三层组织，每层写清「测什么 / 怎么测 / 证据在哪 / 结论」。三层互不顶替：冒烟主链属于**确认测试**，不能拿它冒充单元测试。

### 3.1 单元测试（Unit Test）

| 项 | 内容 |
|---|---|
| 被测单元 | `05_源码/state_machine.py` 状态迁移纯函数；`service.py` 中的权限判定与不变量校验；枚举/字典常量 |
| 测试隔离 | 不启 HTTP、不连数据库，直接调函数；输入 = (当前状态, 事件, 上下文)，断言 = (目标状态 或 抛出的错误码) |
| 用例来源 | 契约 v1 §4 的 8 态 12 条合法迁移全表 + 终态封闭 + I1–I7 |
| 已实跑证据 | 冒烟输出第 4 节「终态封闭与非法迁移」3 项：`重复通过(应40001)`、`已完成单撤销(应40001)`、`不存在单据(应40401)`；第 2 节 `退补缺 comment(应40003)` |
| 结论 | 终态封闭、错误码、必填校验 **4 项实跑通过**；8 态×事件组合的完整单元测试集为 `测试用例表.md` TC-ST-01~13 等 **设计用例，尚未逐条独立执行**，不写作通过 |

**单元测试典型断言（可直接写进报告）**：

```
TC-ST-01  COMPLETED + APPROVE  -> 40001「终态不允许事件」（实跑通过）
TC-ST-02  COMPLETED + CANCEL   -> 40001「终态不允许事件」（实跑通过）
TC-ST-03  UNDER_REVIEW + RETURN(comment 为空) -> 40003（实跑通过）
TC-ST-04  APPROVED + HANDOVER 且无 VERIFY 流水 -> 40003 I7（实跑通过，见 3.2）
TC-ST-05  APPROVED + VERIFY -> APPROVED 自环、状态不变、写 VERIFY 流水（实跑通过）
```

### 3.2 集成测试（Integration Test）

| 项 | 内容 |
|---|---|
| 被测链路 | `Router → Service（事务边界）→ StateMachine → ORM → SQLite`，验证跨层数据一致性 |
| 关键断言 | 每次状态变更同时落 **两张表**（`claim` + `found_item`）与 **一条流水**（`review_record`），防止「接口返回成功但数据没落」 |
| 接口数 | 契约 v1 共 30 条，原型已实现 24 条；本次覆盖 24 条中的主链与越权分支 |
| 已实跑证据 | 冒烟输出第 0–6 节全量；其中第 3 节「通过→核验→交接」6 项、第 5 节「超时批处理」3 项、第 6 节审核历史流水 6 行 |
| 越权集成 | `学生访问队列(应40002)`、`超管访问队列(应40002)` 实跑通过，验证 RBAC 三角色在接口层生效 |
| 结论 | **24 项断言实跑通过、失败 0 项**（两次独立复现：李子研 17:05、组长 21:41），集成主链符合契约 v1 |

**数据一致性证据（贴冒烟第 6 节原文）**：

```
SUBMITTED     --ACCEPT--> UNDER_REVIEW
UNDER_REVIEW  --APPROVE--> APPROVED      | 凭证与物品一致
APPROVED      --VERIFY--> APPROVED       | 核验不通过：到场人与申请人不一致
APPROVED      --VERIFY--> APPROVED       | 核验通过：学号/姓名与申请人一致
APPROVED      --HANDOVER--> COMPLETED    | 已核验学号，现场交接
```

> 这一段同时证明 **I7（交接前必须有核验通过流水）** 与 **VERIFY 是 APPROVED 自环、不改状态**，是答辩最容易被问到的点。
