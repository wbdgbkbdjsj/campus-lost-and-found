## 11. 契约缺口与歧义（执行前须由李子研确认）

这些不是测试的问题，是契约 v0 只约定了「表 + 路径 + 状态机」骨架后必然留下的空白。**建议在《接口文档.md》细化时一次补齐**，否则测试执行时只能"按实际行为记录"，报告会失去判定依据。

| 编号 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| Q1 | 学号重复注册返回什么码？契约只有 40003 参数校验 | TC-AUTH-02 无法判定 | 复用 40003，detail 写"学号已注册"；或新增 40901 |
| Q2 | 登录口令错误返回 40101 还是 40003？40101 定义是"未登录/token 失效" | TC-AUTH-05 无法判定 | 口令错用 40003，token 问题用 40101 |
| Q3 | 同一用户对同一物品重复提交认领，是否允许？ | TC-CLAIM-03 | 建议加唯一约束（found\_item\_id+applicant\_id+非终态），重复提交返回 40001 |
| Q4 | **found\_****item 的 **`CLAIMING`** 状态没有任何动作能触发**。§2.3 状态链写了 REGISTERED→CLAIMING→PICKUP\_PENDING→CLAIMED，但 §4.2 只定义了 APPROVE 时跳 PICKUP\_PENDING | 该状态成为死状态，状态机图与实现不一致，答辩必被问 | 二选一：①删掉 CLAIMING；②首次提交认领时 REGISTERED→CLAIMING，驳回/撤销时回落 REGISTERED。**建议②**，否则 REGISTERED 无法表达"有人在认领中" |
| Q5 | 驳回或撤销后，found\_item 是否回落到 REGISTERED？契约未写 | 物品会永久停在 PICKUP\_PENDING，别人认领不了 | 在 §4.2 伴随动作里补：REJECT/CANCEL/EXPIRE 时 found\_item 回 REGISTERED |
| Q6 | PENDING\_INFO 的 deadline 时长未给（APPROVED 给了 7 天） | TC-REV-09 无法断言具体时间 | 建议 3 天，写进契约 |
| Q7 | `expire-run` 挂在 `/review/` 下但触发者是 system，权限如何判？ | TC-PERM-04 | 约定为 admin 可手工触发（答辩演示需要），或加内部 token |
| Q8 | 列表接口的分页参数名与默认值未约定（page/size 还是 pageNum/pageSize） | TC-FOUND-02 无法断言 | 统一 `page`/`size`，默认 1/10，返回 `total` |
| Q9 | `cancel` 路径在 `/review/claims/{id}/cancel` 下，但触发者是 applicant（A 端用户） | 语义错位：A 端要调 B 端路径，网关鉴权容易误拦 | 建议迁到 `/claims/{id}/cancel`，或明确该路径对 user 角色放行 |
| Q10 | `notification.is_read` 有字段无接口，用户永远读不掉红点 | TC-NOTI-03 | 补 `PATCH /notifications/{id}/read` 与 `read-all` |

> Q4、Q5、Q9 是我认为**必须在编码前定**的三条：Q4 影响状态机图和设计模型，Q5 会造成业务死锁，Q9 会让 A 端联调卡住。
